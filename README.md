🔧 Как устроен пайплайн

Я настроил CI/CD через GitHub Actions в одном файле .github/workflows/ci-cd.yml.

Пайплайн срабатывает на два события:
• push в ветку main — запускает проверки и деплой;
• pull request в main — только проверки, без деплоя.

Пайплайн состоит из двух джоб:

1. lint-and-test — проверочный этап:
   • чекаутим код из репозитория;
   • ставим Node.js 20 (фиксированная версия для воспроизводимости);
   • устанавливаем зависимости через npm ci (а не npm install — так получаем воспроизводимую сборку по package-lock.json);
   • запускаем ESLint — чтобы отлавливать ошибки стиля и потенциальные баги ещё до тестов;
   • запускаем тесты через встроенный node:test.

2. deploy — деплой-этап:
   • запускается только если lint-and-test прошёл успешно;
   • запускается только при push в main, чтобы случайно не опубликовать непроверенный PR;
   • публикует содержимое папки public на GitHub Pages через официальные actions.



📊 Как бы я настроил базовый мониторинг доступности

Для ранней стадии проекта я бы использовал двухуровневый подход без лишнего усложнения:

1. Внешний uptime-мониторинг (например UptimeRobot).
   • Раз в минуту делает HTTP-запрос к главной странице.
   • Ожидает статус 200 и, желательно, наличие ключевого слова на странице (например, «Репетиторы») — это ловит случаи, когда сервер отвечает, но страница пустая.
   • При падении шлёт алерт в Telegram-чат команды или на почту.
   • Бесплатного тарифа UptimeRobot (проверка раз в 5 минут) на старте более чем достаточно.

2. Клиентский мониторинг через Sentry (или GlitchTip, если хочется self-hosted).
   • Ловит необработанные JS-ошибки в браузерах реальных пользователей.
   • Показывает, какие ошибки реально влияют на пользователей, а не просто «падают в консоль».
   • Алертит на появление новых ошибок.

3. Мониторинг самого CI/CD.
   • Если пайплайн в main упал — это тоже инцидент, команда должна узнать об этом сразу.
   • GitHub Actions умеет слать уведомления на почту, либо можно подключить Slack/Telegram через вебхук.


По мере роста проекта (появление Supabase, API, авторизации) добавил бы:
• /health эндпоинт с проверкой подключения к БД;
• мониторинг задержек API;
• алерты на аномальный рост ошибок в Sentry.
